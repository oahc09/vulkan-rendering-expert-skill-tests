## Windows SDK / VVL

1. 固定相同程序和 driver SHA-256，分别记录旧 layer 与包含 `317cff060893783f96d4174f50491e6374eb3714` 的 layer 二进制 SHA-256，验证源码与实际加载的库一致。
2. 同一 queue family 至少两个具有 transfer 能力的 queue，timeline 已启用，Sync Validation 已开启。使用上游 `PositiveSyncValTimelineSemaphore.HostWaitPreservesCrossQueueDependency` 作为正向入口。
3. 负向入口为同一固定源码树的 `NegativeSyncValTimelineSemaphore.WaitInitialValueTwoQueues`。第二队列等待初始值 0，无法获得第一队列 signal 1 的依赖，测试框架要求确实检测到冲突诊断。该用例是独立负控。保留原始日志及退出状态。[固定源码中的负向用例](https://github.com/KhronosGroup/Vulkan-ValidationLayers/blob/317cff060893783f96d4174f50491e6374eb3714/tests/unit/sync_val_semaphore.cpp)

在已准备只用于复验的 ICD、两个已核对的 layer 目录和同一个固定源码的测试程序后，对每个 layer 单独运行下列过滤器。每轮使用新目录保存标准输出、标准错误、退出码和 gtest JSON。两轮保持相同 ICD 和设备身份，以 loader 日志核对实际加载的 layer 文件。下例以 Bash 为例，`$out` 是已创建的新目录：

```sh
VK_LAYER_PATH="$layer_dir" VK_DRIVER_FILES="$icd_manifest" VK_LOADER_DEBUG=layer \
  "$vvl_tests" --gtest_filter=PositiveSyncValTimelineSemaphore.HostWaitPreservesCrossQueueDependency \
  --gtest_output="json:$out/positive.json" > "$out/positive.log" 2>&1
printf '%s\n' "$?" > "$out/positive.exit"
VK_LAYER_PATH="$layer_dir" VK_DRIVER_FILES="$icd_manifest" VK_LOADER_DEBUG=layer \
  "$vvl_tests" --gtest_filter=NegativeSyncValTimelineSemaphore.WaitInitialValueTwoQueues \
  --gtest_output="json:$out/negative.json" > "$out/negative.log" 2>&1
printf '%s\n' "$?" > "$out/negative.exit"
python -X utf8 tools/evidence19.py vvl-host-wait "$out/positive.json" --control positive
python -X utf8 tools/evidence19.py vvl-host-wait "$out/negative.json" --control negative
```

确认固定 layer 的正例执行后通过，负例执行后由 gtest 验证预期冲突。旧 layer 只有在实际出现对应错误时才登记假阳性差异，其他失败单独调查，跳过仍为未运行。JSON 适配器核对固定的测试名及状态，保留 SHA-256；实际加载的 layer、测试二进制和设备身份另附记录。

固定源码标签分别为 `vulkan-sdk-1.4.363.0` 的 `15c64e73db67e27ff0215708fbe48684a35c6827` 和 `vulkan-sdk-1.4.363.1` 的 `317cff060893783f96d4174f50491e6374eb3714`。[LunarG 发布说明](https://vulkan.lunarg.com/doc/view/latest/windows/release_notes.html) · [VVL 源码与正向用例](https://github.com/KhronosGroup/Vulkan-ValidationLayers/commit/317cff060893783f96d4174f50491e6374eb3714)

WSL 下使用同仓 `probes19/device_capabilities.c` 与固定 1.4.368 headers，只枚举显式选择的 lavapipe 软件 ICD。实际测得 transfer-capable 队列族只有 1 个队列，未达到正控所需的同族 2 队列。原始设备库存、编译器版本、ICD/driver/loader 哈希在 `reports/v21-implementation-2026-11-28/vvl-lvp-capability/`。这项执行是能力查询，A/B 正反例状态仍为 `NOT_RUN`。

Windows 的 `vulkaninfo --text` 成功查询 Intel Graphics 和 RTX 5060，两者都有明确公布 transfer 能力且至少包含 2 个队列的族。设备库存 SHA-256 为 `189d79cb8b4140009268bd9326149e9dbe90f9448de2021aa93ee40e1e476a98`，原始结果在 `reports/v21-implementation-2026-11-28/vvl-windows-capability/`。Host 解析正反例可复验固定名称与跳过、通过、冲突结果。

### 实际 SDK 二进制对照

从 LunarG 两份固定 Windows x64 安装包离线提取 VVL DLL 与 manifest。旧包核对有效的 LunarG 签名与下载哈希，修复包按官方 SHA-256 核对。两个安装程序均未执行，测试进程逐轮使用独立 `VK_LAYER_PATH`。实际 DLL 加载路径以 loader 日志核对。[官方 SDK 下载信息](https://vulkan.lunarg.com/sdk/home)

同一 `probes19/vvl_host_wait21.c` 构建和同一 RTX 5060 driver，在同一 transfer-capable queue family 申请两个队列。探针采用官方正例的有效 A → B → A 提交和 host wait 顺序。发生验证错误时 callback 拒绝该调用，后续保留原始诊断和返回码。

| 实际 VVL | 最后一轮 A | 诊断 |
|---|---|---|
| SDK 1.4.363.0 | 回调中止，`VK_ERROR_VALIDATION_FAILED_EXT` | `SYNC-HAZARD-WRITE-AFTER-WRITE` |
| SDK 1.4.363.1 | `VK_SUCCESS` | 0 errors |

可在 VS 开发 PowerShell 中以 `cl /std:c11 /W4 /WX /I<固定 headers> probes19/vvl_host_wait21.c <SDK>/Lib/vulkan-1.lib` 构建。逐轮选择从对应 SDK 提取的 layer 目录，保持同一能提供两队列的设备与 loader。原始日志及确切身份保存在 `reports/v21-implementation-2026-11-28/vvl-363-ab/`，回执 SHA-256 `703504690d735986f0ea0e1d65b17257709b50049ac44984934a22e2e744c0b9`。运行用的是合法提交的独立小探针。上游完整 gtest 及其故意缺同步的负向用例仍记为 `NOT_RUN`。

### Mock ICD 独立负控

用同一探针的 `/DV21_MOCK_NEGATIVE` 构建，在 Khronos Mock ICD 的同一队列族中提交两个写同一缓冲区的命令。队列 A 发出 binary semaphore，队列 B 缺少对应等待。探针要求只枚举到指定 Mock 设备才会继续，loader 日志复核 ICD、实际加载的 VVL 路径以及未插入 NVIDIA 隐式层。

| VVL | 队列 B 的诊断 | 提交结果 |
|---|---|---|
| SDK 1.4.363.0 | `SYNC-HAZARD-WRITE-RACING-WRITE` | 验证回调中止，`VK_ERROR_VALIDATION_FAILED_EXT` |
