## 1. 最终目标与版本关系

v1.0.19 不只是“再增加四个工作流”，也不是把已有内容换标题再写一遍。最终目标是形成以下完整能力链：

```text
需求/故障/仓库
→ 完整Vulkan知识与能力边界
→ 项目、设备及负载画像
→ 有依据的GPU方案决策
→ 代码/日志/capture/trace证据
→ 假设与可反驳实验
→ 授权后的最小实现或修复
→ 正确性、画质、性能及回归验证
→ 可审查交付
→ 经核验、可撤销的经验沉淀
```

| 版本 | 原有职责 | 本版如何承接 |
|---|---|---|
| v1.0.16及之前 | API、调试、架构、移动端、内容链路、GPU-driven、画质、透明与仿真 | 保留并回归；新增能力复用既有Resource/Descriptor/Pipeline/Queue/生命周期体系 |
| v1.0.17 | Vulkan本体全域覆盖、规范一致性与阶段验收 | 已完成则复用审计结果；未完成的冻结范围缺口明确纳入本版，禁止假定已经闭环 |
| v1.0.18 | 文字、矢量与2D/3D融合 | 保持独立业务专题归属；在最终能力清单中集成，不再把文字变成全局预读 |
| **v1.0.19** | **全域知识、决策、执行、经验与交付的最终整合** | **不再把稳定范围内的重要缺口挪到下一功能版本** |

“收尾”表示验收有明确分母和结束条件，不表示永远冻结Vulkan规范，也不表示未来所有硬件未经测试就被覆盖。

## 3. “Vulkan能涉及的都补齐”的范围合同

### 3.1 全量登记，不按热点或常用度删减

官方Registry描述API元素及其版本、扩展和依赖，是范围清单依据；规范正文及Reference Pages承担使用语义依据。不能只凭关键词命中、API文件数或题数证明完整性。[S1、S3]

| 范围 | 本版要求 |
|---|---|
| 标准Vulkan Core | 冻结快照中的1.0–1.4及修订差异，全部登记；实施时出现新核心版本需先更新范围合同，不静默假定 |
| 公开KHR/EXT/厂商/平台扩展 | 全量分类；每项有自己的能力、依赖、语义差异和使用/拒绝/回退规则 |
| 核心晋升、别名、弃用和替代 | 保留历史兼容映射；避免重复计数或误认为晋升后所有feature自动启用 |
| Provisional/Beta | 独立预览清单，说明接口稳定性和编译/驱动前提；不能算作稳定硬件支持 |
| disabled/预留编号/非公开接口 | 显式排除和记录理由，不凭名称补造规范 |
| SPIR-V及编译链 | 覆盖Vulkan目标环境、能力、布局、接口、内存与执行约束及编译/验证过程；不重写所有源语言编译器 |
| Loader/ICD/Layers/Profiles/工具 | 覆盖应用加载、层注入、dispatch、多实例/多Device、能力查询、捕获回放与诊断边界 |
| **Vulkan SC** | 单列官方API变体、版本和差异清单，复用共性并补静态资源规划、离线pipeline、受限操作与fault等工作流；与标准Vulkan分母及验证结果分开，不声明安全认证。[S12] |
| OpenXR/OpenCL/CUDA/D3D/Metal/媒体平台 | 覆盖与Vulkan的能力匹配、资源、同步、所有权、生命周期及迁移边界；不声称这些外部标准的所有功能属于本技能完整性分母 |
| 已有业务专题 | 架构、系统渲染、Shader/资源、GPU-driven、光照、透明/3DGS、仿真、文字全部登记、路由与回归 |

本版交付的是完整专家知识、决策流程、工具适配与真实工程交付能力，不是另行实现完整GPU驱动、操作系统、软件视频编解码器、字体解析器或通用物理引擎。其与Vulkan相关的接口和限制仍须覆盖。

### 3.2 同一条目有四种深度，不能偷换

| 标识 | 深度 | 本版验收 |
|---|---|---|
| L0 | 清单和路由 | 规范、版本、扩展和知识锚点存在；别名/排除原因清楚 |
| L1 | 语义合同 | 支持/启用、依赖、生命周期、同步/host线程、参数边界、失败和兼容有实质内容 |
| L2 | 工程能力 | 对所属功能族提供实施、排错、选择/拒绝/回退及验证路径；扩展差异不能被公共文章掩盖 |
| E | 执行证据 | 分别记录代码检查、编译、CPU、Vulkan、模型、宿主、设备、视觉和性能结果 |

全部纳入条目必须L0；公开稳定能力必须L1；核心域和稳定功能族必须L2，单个增量扩展可以复用公共L2但须补自己的差异。已知未写完的稳定能力不能标N/A。硬件缺失不豁免L1/L2；反过来，L2完成也不代表E已通过。

### 3.3 必须冻结的分母

冻结`vk.xml`、相关`video.xml`、规范正文、Reference/VUID数据、Vulkan-Headers、SPIR-V Registry/Headers及工具版本，并保存hash。按API变体、平台、稳定性和规范版本独立计数。

机器扫描至少识别命令、类型、成员、枚举、feature、properties/limits、依赖表达式、pNext合法性、别名和版本归属。VUID数量巨大时建立可检索映射与风险驱动测试，不声称每个VUID都已有独立GPU测试。

```text
登记率 = 已分类且可路由的纳入条目 / 冻结范围条目
语义完成率 = 达到约定L1/L2的条目或功能族 / 对应冻结分母
交付成功率 = 实际解决且通过独立判据的执行任务 / 预登记可执行任务
设备覆盖 = 平台×GPU/driver×功能路径×场景的明细，不压成全硬件一个百分比
```

登记率、稳定语义完成率目标100%；这些是计划验收目标，不是本轮测得结果。没有清单或实际执行记录时值为未知，不填写估计百分比。

## 7. C1：规范知识从“有条目”提升到“可用且无冲突”

### 7.1 每个功能族的知识合同

```text
用途与非用途
→ 核心/扩展/平台/SC变体
→ 支持查询与启用条件
→ 对象、资源、布局与host线程归属
→ 正常调用顺序
→ 并发、跨帧与跨queue约束
→ 失败、取消与恢复
→ 已知工具覆盖缺口
→ 性能取舍与fallback
→ 可执行验证
```

官方链接不能代替上述正文；但也不逐字段复制Spec。共享部分引用公共权威段落，特例必须准确表达且可单独检索。

### 7.2 机械扫描与语义审查分开

机械扫描适合验证符号存在、结构体字段归属、宏/别名、VUID对应对象、版本、依赖表达式和链接。语义审查检查“规则是否适用当前路径”，例如支持/启用混淆、workgroup与dispatch同步混淆、submit与presentation退休混淆等。两者不能互相代替。

Registry解析须处理AND/OR及括号、API变体、protect/platform条件、alias、promoted/deprecated/obsoleted、require/remove等实际schema；不要把extension名字拼成线性列表即认为依赖满足。[S1]

### 7.3 必须修正的已知风险类型

未知枚举或伪字段；规范中的MUST与工程建议混写；只按API版本宣称feature已启用；把特定GPU经验推广到所有设备；把布局等同于同步；把host coherent等同于无需生命周期依赖；把Query结果就绪与提交完成混写；把工具clean当正确性证明；把普通纹理与Surface绑定为规范前提。

本轮官方1.4.368修订说明包括撤回`maxPushDescriptors`曾增至32的旧描述，以及EXT/KHR fault报告调用关系的补充。实施时搜索实际受影响位置，不预先宣称仓库必有对应错误。[S2]

## 8. C2：GPU决策引擎——先证明可行，再决定是否值得

这里的“引擎”是可解释规则、结构化合同和验证器，优先嵌入现有工作流；不是另建常驻服务或自动修改所有项目的进程。

### 8.1 输入画像

| 输入 | 必需字段/事实 |
|---|---|
| 设备 | OS/API、GPU/deviceID、driver/UUID、实际Vulkan版本、queue、memory heaps、limits与format能力 |
| 已启用状态 | 创建Instance/Device时实际enabled extensions/features；不得仅由物理设备支持反推 |
| 工作负载 | scene/pass图、draw/dispatch规模、分辨率、覆盖/重叠、资源更新、计算与graphics依赖 |
| 产品约束 | 平台范围、首屏/帧预算、质量误差、延迟、内存、持续热状态、依赖与维护成本 |
| 工程现状 | 可复用的资源/descriptor/pipeline/queue管理、老设备回退、代码变更范围 |
| 测量 | 当前capture/trace/counter/A-B证据及其时间、配置、覆盖与误差 |

支持、已启用、参数组合允许和性能收益是不同字段，不能用一个`supportsVulkan14`布尔值替代。Vulkan Profiles可以组织能力基线，但不证明应用实际已经启用或某个方案在本负载更快。[S10]

### 8.2 决策过程

```text
候选方案集合
→ API/设备/资源/平台硬约束过滤
→ 数据依赖、生命周期与质量约束过滤
→ 比较成本及证据等级
→ 选择最小必要方案或保留原方案
→ 给出最小验证实验
→ 实测后决定启用、撤销或继续保持条件路径
```

未知能力标`UNKNOWN`，不是`true`。方案暂不具备证据标`NEEDS_MEASUREMENT`，不编造精确得分或概率。质量、延迟、功耗、内存和复杂度不可被一个没有依据的“综合分”掩盖；没有用户权重时可输出不被其他方案全面优于的候选和明确取舍。

### 8.3 必须纳入的决策族

| 决策族 | 候选与边界 |
|---|---|
| 渲染组织 | RenderPass/subpass、Dynamic Rendering/local read、手工pass与RenderGraph |
| 资源绑定 | 传统set、push、indexing/bindless、descriptor buffer/heap；不能视为自动升级阶梯 |
| 计算调度 | Graphics/Compute、单queue/多queue、同步表达与真实overlap |
| 内存与加载 | 全驻留/流式/sparse、staging/host-copy/外部资源、alias/retire、格式/压缩/精度 |
| pipeline成本 | 预热/cache/binary/GPL、动态状态、shader object及其支持与复杂度 |
| 规模化 | CPU合批、GPU固定槽、compact/count、Mesh/DGC；规模和覆盖分别测量 |
| 画质 | shadow map/屏幕空间/query/full RT、MSAA/TAA/SR、透明方案与中间精度 |
| 移动持续性能 | 更新频率/分辨率/采样/LOD、热状态回退、帧节奏与输入延迟 |
| 内容与平台 | 原生Video/平台codec、Camera/AHB、外部计算、XR、神经原生/仿真/传统fallback |
| 仿真与文字 | 求解并行方式、状态快照、bitmap/MSDF/mesh、系统能力与最少依赖 |

每条规则包含：`rule_id / inputs / prerequisites / decision / alternatives / evidence / fallback / revisit_conditions / tests / version_scope`。这是拟议内部字段，不是Vulkan API。

### 8.4 验收反例

同一GPU不同负载必须可能得到不同方案；同一负载不同设备不得一律选择相同新技术。没有multiDrawIndirect或某format特性时能合法降级；异步Compute单pass更快但全帧更慢时能撤销；性能证据不足时能保留旧路径。按厂商品牌硬编码“永远更好”不通过。

## 9. C3：证据总线与薄工具适配

### 9.1 统一证据记录

```json
{
  "evidence_id": "ev-local-001",
  "kind": "validation|capture|trace|code|image|measurement",
  "run_id": "immutable-run-id",
  "skill_sha": "pinned-sha",
  "project_sha": "pinned-sha",
  "tool": {"name": "actual-tool", "version": "actual-version"},
  "device_scope": "recorded-device-and-driver",
  "object": {"id": "engine-resource-id", "generation": 3},
  "frame_submit_event": "available-identifiers-or-null",
  "source": {"path": "actual-file", "symbol": "actual-symbol", "lines": "verified-range"},
  "artifact_sha256": "actual-hash",
  "observation": "direct-observation",
  "limitations": ["explicit-coverage-gap"]
}
```

字段是计划合同。不能把缺失frame、资源ID或源码位置虚构补满。CPU/GPU时钟与capture event不是天然相同时间轴，只有校准或明确关联才能串联；资源handle复用必须加generation/设备/运行作用域。

### 9.2 工具接入策略

| 入口 | 本版产物 | 边界 |
|---|---|---|
| Vulkan Validation / SyncVal / GPU-AV | 配置、版本识别、结构化日志、VUID/访问关联和能力覆盖 | 不把零错误视作程序正确；诊断插桩成本不当优化成本 |
| RenderDoc | 已有Python API的薄调用，提取事件、管线、绑定资源和相关图像 | 不假设所有扩展、平台、protected内容或设备丢失都可capture/replay |
| Perfetto / 系统trace | 固定SQL/查询模板、线程/提交/呈现/热状态关联 | 数据源存在、权限和时间域单独检查 |
| GFXReconstruct等回放 | 按项目支持范围保存重放步骤与依赖 | 回放成功不证明所有线程竞态或系统生命周期已复现 |
| 编译与CPU工具 | 原构建系统、SPIR-V工具、内存/线程检查器按环境复用 | 不强制引入新构建系统；真实环境记录 |
| GPU厂商工具 | 可用时解析相关counter和fault证据 | 不比较未统一定义的跨厂商counter数值 |

RenderDoc提供Python脚本接口；Perfetto Trace Processor支持脚本化trace分析；SyncVal提供比自然语言报错更适合解析的附加属性。应复用这些能力，不重做抓帧器和性能平台。[S6–S9]

至少交付可测试的Validation解析与一种capture/trace适配，并保留无图形工具时的源码、日志与最小复现路径。工具缺失、版本不匹配或权限不足时明确停止该验证步骤，不伪造文件或成功记录。

## 10. C4：因果诊断、实验规划与最小修复

### 10.1 假设账本

| 字段 | 要求 |
|---|---|
| 现象与范围 | 首次发生条件、频率、设备/driver、受影响pass/资源 |
| 假设 | 具体机制，不能只写“同步问题” |
| 支持证据 | 直接代码/工具观察，引用evidence_id |
| 反证与未解释现象 | 主动列出矛盾、缺失路径和可替代解释 |
| 区分实验 | 最小变量改变、预测结果、风险与资源预算 |
| 判定 | 支持/反驳/仍不足，不以现象暂时消失自动升格 |
| 下一步 | 撤销假设、继续取证、临时绕过、最小修复或结构修复 |

加入`vkDeviceWaitIdle`后故障消失，只是改变了并发与时序。必须继续区分resource reuse、descriptor更新、queue依赖和提前回收；没有实验不能认定“保留WaitIdle就是修复”。这是本版诊断规则，不是一条特定项目的已证实根因。

### 10.2 允许的实验与停止条件

优先日志、确定性小场景、参数减半、合法路径切换和CPU参考。每次实验写出“希望区分什么”，避免随机试改。保护内容、客户数据和生产设备不用于未经授权的压力或故障注入。

设置运行次数、timeout、内存、token与变更面预算。遇到设备失联、原始资料损坏、未授权依赖、相互矛盾证据或错误预算超限时停止并保存证据；不能以赶进度为理由扩大权限。

### 10.3 Patch合同

```text
复现及修改前证据
→ 根因机制与反证说明
→ Must/Should/Can Defer/Do Not Change
→ 最小patch与依赖顺序
→ 正常、失败、取消与旧代际路径
→ 针对性回归
→ 全影响面回归
→ 回滚方式与剩余风险
```

不把结构修复强塞进最小bug修复；必须改变架构时另列原因和迁移风险。新代码优先复用已有管理器，不新建平行Device/queue/resource系统。

“修复前失败、修复后通过”是优先证据；偶发缺陷记录复现频率、样本量和观察时长，不把一次不复现包装成根除。没有运行环境可以交付未验证patch，但不能标“已解决”。

## 11. C5：性能、画质、内存、热状态联合优化

### 11.1 优化必须回答五个问题

瓶颈证据是什么；候选实际减少哪类工作；增加了什么成本；正确性/画质/延迟是否变化；在可比条件下全帧与持续运行是否值得。

分别记录CPU工作、GPU pass、submission/wait、present节奏、内存峰值、输入/显示延迟、画质与可获得的功耗/热数据。不能用短时平均FPS、单个pass或生成帧FPS替代产品目标。

### 11.2 A/B合同

固定项目版本差异、scene/seed、相机和输入序列、分辨率、目标质量、缓存冷热状态、设备/driver及预热策略。温度/功率模式/后台负载记录而非忽略；A/B顺序与重复次数预登记，报告原始结果和波动。

诊断插桩、Validation、capture与性能测量模式分开。能量、带宽或counter不可用时标不可测；不能从帧耗时简单推导节电率。无显著收益时推荐不改动是合法结果。

### 11.3 持续策略与退出条件

按产品预算提供分辨率、采样、LOD、更新频率、透明层数、仿真频率等可回退档位，加入迟滞和重新评估条件，避免每帧频繁切档。切档会影响history、pipeline/resource generation与输入时序，必须同步说明。

优化验收在M0固定目标和可接受退化上界，不预设“提升30%”等通用GPU收益。此前原始12题模型input-token目标单独保留，不能与渲染性能混用。

## 12. C6：生产可靠性、可移植性与受限场景

| 场景 | 必须给出的行为 |
|---|---|
| 初始化/功能不可用 | 返回码、可选feature、版本/format失败有明确fallback；不使用未初始化句柄 |
| 分配失败/内存压力 | 按最后使用回收，停止新增负载，退级或受控退出；不能释放in-flight对象 |
| 异步取消/切场景 | 任务、资源和Device generation关联；迟到结果不能发布到新场景 |
| Shader/pipeline编译或缓存失败 | 保留兼容旧路径，缓存验证与重新创建；错误不得污染整库 |
| Surface变化/多实例 | 停止受影响输出，确认事件，区分局部WSI失效与共享Device故障 |
| Device lost | 收集可用fault/提交证据、停止不合法继续执行、按项目策略重建设备或结束；不保证就地恢复 |
| 跨API/跨Device | 内存、同步载荷、所有权、UUID/driver、所有消费者退休分别验证 |
| 稀疏/别名/保护 | 查询、绑定、驻留、范围与访问限制明确；保护内容不得强制回读/抓帧 |
| Video/XR | session/swapchain、DPB/view、格式、队列、时间与所有权按各自合同，不复用不适用WSI假设 |
| Driver规避 | 只针对可定位device/driver/version/特性签名，有证据、到期或重测条件；不按品牌永久禁用 |
| 层/工具/多ICD | loader dispatch和配置来源可追溯；错误注入层不能悄悄改变真实能力报告 |
| 资源输入 | shader、纹理、PLY、字体、路径、模型及缓存有大小/格式/处理预算，不信任任意输入 |

受控故障实验可用mock返回码、取消点、allocator失败和可预测timeout模拟；必须标为CPU/fixture证据。真实GPU挂死、系统权限、驱动替换和DRM受保护路径测试另须明确授权。

兼容矩阵按OS/GPU/driver/API/feature/format/工具/路径填写。至少定义Android Adreno、Android Mali及一个桌面实现的核心回归矩阵；实际设备缺失时对应格为BLOCKED/UNVERIFIED，不假装通过。其他平台及特殊能力按声明的支持范围验证，不宣称全部移动GPU通用。

## 13. C7：可追溯经验系统

### 13.1 经验不是新的规范来源

每条经验包含：问题签名、项目/平台/设备/driver/源码与工具版本、原始证据、机制、最小修复、回归结果、反例、适用条件、失效条件、审核状态。官方语义与经验并存时优先规范；项目源码只证明项目实现。

```text
运行记录
→ 候选case
→ 去敏与来源核查
→ 复现/反例审查
→ 接受为限定范围经验
→ 定向检索使用
→ 新证据冲突后降级/撤销/替换
```

测试失败和未复现经验必须保留；“某设备有效”不能提升成全平台规则。外部issue、作者猜测、上游PR未合并和本地复现是不同状态。

### 13.2 检索与反馈

先按设备/driver、feature和访问模式硬匹配，再按现象与项目相似度排序。输出为何适用、哪些条件未匹配及下一验证，不只展示最相似标题。

实验结果只能修订其对应范围；禁止自动改模型路由、扩大工具权限或将一次回答写为硬规则。没有稳定实验，不自动调高置信度。新增case后检查是否需要修正playbook、workflow或决策规则，避免经验散落。

### 13.3 隐私、许可与污染隔离

默认本次运行本地保存，持久化和公开入库需相应授权与审核。不得把客户源码、GPU capture、相机帧、账号信息或私有数据自动上传。原始证据、公开总结和运行时知识分层存储。

案例训练/开发集与盲测集按项目、根因模式及修复历史分离；不是换几个类名就算新问题。标准答案、原始patch、评审rubric不得注入被测模型。新案例不得污染冻结的对照集。

## 20. 评分、防污染与成功判据

### 20.1 全域知识门

全部纳入条目登记；稳定语义达到L1/L2要求；已知P0/P1规范性缺陷清零；规范、API、workflow、case无已知关键冲突。关键缺陷包括非法API/feature组合、错误生命周期/同步、数据损坏、证据造假和越权执行。

### 20.2 实战门

预登记的核心可执行任务必须满足独立判据，不使用“有patch”作为成功。评审检查机制正确性、修改最小性、回归覆盖、资源清理、未验证说明和新增风险。核心任务有FAIL时不通过实战门；因环境缺失BLOCKED与模型失败分开，但也不标实战全通过。

对重要模型行为，建议同模型/参数/工具权限进行至少三次独立运行，作为拟议稳定性检查而非通用统计保证。记录重复间分歧，根因/权限/数据安全类错误不靠平均分抵消。

### 20.3 对照与成本

基线优先采用实际可运行的v1.0.17/1.0.18候选；若尚不存在，记录所选前版及缺失能力，不伪造基线。模型、prompt、工具、设备与预算一致；不同根因与项目隔离避免记忆标准patch。

报告解决率、错误根因率、回归引入、无效实验次数、实际tokens/时间及工具成本。正确拒绝不支持/未授权路径单独计分，不与已解决混加。原始12题token对照保持历史定义，不能用新混合题中位数刷新百分比。
